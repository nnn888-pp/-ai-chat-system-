### 1.1 关键设计原则

1. **模型与业务解耦**：路由/服务层只依赖 `ModelProvider` 接口，新增模型只加 provider 或配置。
2. **本地模型进程内单例**：一个模型只加载一次，用 `asyncio.Lock` 串行保护生成，避免并发把显存打爆。
3. **数据库可切换**：所有表通过 SQLAlchemy ORM 定义，SQLite/MySQL 仅连接串不同。
4. **后端优先**：先跑通鉴权 → 会话 → 消息 → 模型，再接前端。

## 5. 模型适配层

### 5.1 统一接口

```python
class BaseProvider(abc.ABC):
    key: str                 # 全局唯一，如 "remote:deepseek-chat" / "local:qwen-lora-wukong"
    name: str                # 展示名
    kind: str                # "remote" | "local"
    description: str = ""

    def get_status(self) -> ProviderStatus: ...   # ready / unloaded / loading / failed + error_msg
    def generate(self, messages, *, max_new_tokens=256, temperature=0.7, top_k=20) -> str: ...
    def load(self) -> None: ...                   # 预热；默认在 generate 内懒加载
    # generate_stream：V2
```

### 5.2 ModelRegistry

职责：
1. 启动时读取 `.env` 中的 `REMOTE_MODELS_JSON`（远端模型列表）+ 扫描 `models_store/`（本地模型）。
2. 按 `model_config.json` 的 `kind` 分发：`hf_qwen` / `hf_qwen_lora` → `QwenLoRAProvider`，其余（含 `local_custom`）→ `LocalPTProvider`；配置解析失败时降级为 `MockProvider` 并在列表里显式标错。
3. `get(key)` 懒加载：本地模型首次调用时才真正加载权重，并加入缓存字典。
4. `refresh()`：重新扫描目录，供前端"刷新模型"调用；已加载实例不重复加载。
5. 目录为空时挂一个 `mock:default`，保证系统仍可演示。

### 5.3 本地模型加载策略

**A. 自研小 GPT（`kind: local_custom`，产品要求保留的原生 `.pth`）**

- 用 `training/model.py` 的 `GPTModel` 结构 + `torch.load(ckpt_path)` 加载权重，tokenizer 用 `training/tokenizer/tokenizer.json`。
- 提示词模板 `"问：{question}\n答："`，只把最后一条用户消息套入模板；模型是续写式，不做多轮拼接。
- 采样：`temperature=0.8`、`top_k=10`、`max_new_tokens=40`（小模型输出短，避免跑飞）。

**B. Qwen + LoRA（`kind: hf_qwen` / `hf_qwen_lora`）**

- `AutoModelForCausalLM.from_pretrained(base_model_path)`，LoRA 再 `PeftModel.from_pretrained(base, lora_path)`（不 merge，便于切换 adapter）。
- `prompt_format` 决定推理方式：
  - `chat`：走 `tokenizer.apply_chat_template`，**仅适用于 Instruct 基座**。
  - `raw_completion`：裸文本续写（"问：…答："），**基座模型必须用这个**，否则 chat 模板属于分布外输入，会输出生僻字。
- `prepend_text` 可在问题前注入身份前缀（如"下面以孙悟空的口吻回答问题"）。
- 基座 + 小数据集 LoRA 时用 `temperature=0`（贪婪解码）保证输出稳定；生成中出现第二个"问：/答："即截断，避免自问自答。
- 推理在 `run_in_executor` 线程池执行，provider 内部 `threading.Lock` 串行保护。
- 加载失败置 `failed` + `error_msg`，接口返回可读信息，不影响其他模型。
- **禁止**：不调用 llama.cpp / Ollama 加载自有 `.pt`；Ollama 仅作为 V2 可选的第三方本地模型入口。

## 6. 鉴权与安全

1. 注册：`bcrypt.hashpw(password.encode(), bcrypt.gensalt())`，入库 60 字符哈希。
2. 登录：`bcrypt.checkpw` 校验，签发 JWT（payload：`sub=user_id`, `exp=7d`）。
3. 请求：`Authorization: Bearer <token>`，`deps.get_current_user` 解析并查库校验用户存在。
4. 越权防护：所有会话/消息查询条件**必须带 `user_id`**，不靠前端传参判断归属。
5. 传输加密：前端登录前对密码做一次 `SHA-256(明文 + 固定盐)`，后端再做 bcrypt。这样即使明文 HTTP 也不直接暴露原始密码；生产环境应叠加 HTTPS。口径已定稿（见 PRD Q-1）。
6. 密钥管理：远端模型 API Key 只放 `.env`，`/api/models` 响应中脱敏为 `sk-****abcd`。
7. CORS：开发期允许 `http://localhost:5173`，交付前收紧。

## 7. 关键流程

### 7.1 登录

```
前端表单 → SHA-256(密码) → POST /api/auth/login
→ 后端查 user → bcrypt.checkpw → 签发 JWT
→ 前端存 localStorage(token) → 路由跳 /chat
```

### 7.2 发送消息

```
POST /api/conversations/{id}/messages {content, model_key?}
→ 校验会话归属 → 落库 user 消息
→ 取该会话历史，只保留「user 消息 + 当前模型自己生成的 assistant 消息」，截断到最后 10 轮
   （同一会话切换过模型时，避免其它模型的输出（尤其小 GPT 的续写）污染上下文）
→ registry.get(model_key)
→ provider.generate(messages)（本地走线程池 + 线程锁）
→ 落库 assistant 消息（含 model_key、status）
→ 更新 conversation.updated_at
→ 返回 {user_message, assistant_message}
```

### 7.3 会话切换模型
只更新 `conversations.model_key`，不改历史消息；新消息使用新模型。

## 9. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 本地模型显存/内存不足 | 加载 OOM、进程退出 | 单模型单例、`torch_dtype=auto`、限制 `max_new_tokens`、加载失败只标记不崩溃 |
| 本地模型加载慢 | 首次请求超时 | 首次调用前先"加载模型"接口预热，前端显示状态 |
| 远端模型不稳定 | 429/超时 | 统一捕获异常转成 502 + 可读文案，前端提示重试 |
| pt 格式兼容问题 | `from_pretrained` 参数不匹配 | 先写测试脚本实测跑通，再接入系统；自研 GPT 直接用 `torch.load` + `GPTModel` 结构 |
| 前后端字段不一致 | 联调返工 | 以 `docs/API设计.md` 为准，后端先出 OpenAPI，前端按 schema 生成 |
| 并发生成导致锁等待 | 多标签页同时发 | 锁 + 明确排队提示，V2 再做队列与流式 |
| 基座模型输出乱码 | 生僻字重复、角色乱串 | 基座一律走 `raw_completion` 裸续写；`temperature=0` 贪婪解码；生成中出现第二个"问：/答："即截断 |
