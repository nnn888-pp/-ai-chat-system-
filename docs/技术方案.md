### 1.1 关键设计原则

1. **模型与业务解耦**：路由/服务层只依赖 `ModelProvider` 接口，新增模型只加 provider 或配置。
2. **本地模型进程内单例**：一个模型只加载一次，用 `asyncio.Lock` 串行保护生成，避免并发把显存打爆。
3. **数据库可切换**：所有表通过 SQLAlchemy ORM 定义，SQLite/MySQL 仅连接串不同。
4. **后端优先**：先跑通鉴权 → 会话 → 消息 → 模型，再接前端。

## 5. 模型适配层

### 5.1 统一接口

```python
class BaseProvider:
    key: str            # 全局唯一，如 "remote:zhipu:glm-4" / "local:my-lora"
    name: str           # 展示名
    kind: str           # "remote" | "local"

    def generate(self, messages: list[dict], **params) -> str: ...
    def generate_stream(self, messages: list[dict], **params): ...  # V2
```

### 5.2 ModelRegistry

职责：
1. 启动时读取 `MODELS_CONFIG`（远端模型列表）+ 扫描 `models_store/`（本地模型）。
2. 对每个模型的 `model_config.json` 做校验，产出元信息：`key / name / kind / base_model / adapter_path / max_new_tokens / device`。
3. `get_provider(key)` 懒加载：本地模型首次调用时才真正 `from_pretrained`，并加入缓存字典。
4. `refresh()`：重新扫描目录，供前端"刷新模型"调用；已加载实例不重复加载。

### 5.3 本地模型加载策略

- **全量微调产物**：目录内 `model_config.json` 标记 `"type": "full"`，用 `AutoModelForCausalLM.from_pretrained(dir)` + `AutoTokenizer.from_pretrained(tokenizer_dir)`。
- **LoRA 产物**：标记 `"type": "lora"`，先加载 `base_model`，再 `PeftModel.from_pretrained(base, adapter_dir)`；若显存紧张可 `merge_and_unload()` 后再推理。
- **推理调用**：`tokenizer.apply_chat_template(messages, ...)` 拼 prompt → `model.generate(...)` → `decode(skip_special_tokens=True)`。
- **并发控制**：同一 provider 上挂 `threading.Lock`，生成在 `run_in_executor` 线程池执行，避免阻塞事件循环。
- **异常兜底**：加载失败置状态 `failed` 并记录 `error_msg`，接口返回可读信息，不影响其他模型。
- **禁止**：不调用 llama.cpp / Ollama 加载自有 `.pt`；Ollama 仅用于 V2 接入第三方开源小模型。

### 5.4 本地模型目录约定

```
models_store/<model-key>/
├─ model_config.json
├─ tokenizer/                 # tokenizer 文件
├─ model.safetensors | pytorch_model.bin   # full 类型
└─ adapter_model.safetensors  # lora 类型（可选 tokenizer 覆盖）
```

`model_config.json` 示例：

```json
{
  "name": "我的Qwen-LoRA",
  "type": "lora",
  "base_model": "Qwen/Qwen2.5-0.5B-Instruct",
  "adapter_path": "./",
  "tokenizer_dir": "./tokenizer",
  "device": "auto",
  "max_new_tokens": 512,
  "temperature": 0.7
}
```

## 6. 鉴权与安全

1. 注册：`bcrypt.hashpw(password.encode(), bcrypt.gensalt())`，入库 60 字符哈希。
2. 登录：`bcrypt.checkpw` 校验，签发 JWT（payload：`sub=user_id`, `exp=7d`）。
3. 请求：`Authorization: Bearer <token>`，`deps.get_current_user` 解析并查库校验用户存在。
4. 越权防护：所有会话/消息查询条件**必须带 `user_id`**，不靠前端传参判断归属。
5. 传输加密：前端登录前对密码做一次 SHA-256（加固定盐），后端再做 bcrypt。这样即使明文 HTTP 也不直接暴露原始密码；生产环境应叠加 HTTPS。口径待 PRD Q-1 确认。
6. 密钥管理：远端模型 API Key 只放 `.env`，`/api/models` 响应中脱敏为 `sk-****abcd`。
7. CORS：开发期允许 `http://localhost:5173`，交付前收紧。

## 7. 关键流程

### 7.1 登录

```
前端表单 → SHA-256(密码) → POST /api/auth/login
→ 后端查 user → bcrypt.checkpw → 签发 JWT
→ 前端存 localStorage(token) → 路由跳 /chat
```

### 7.2 发送消息

```
POST /api/conversations/{id}/messages {content, model_key?}
→ 校验会话归属 → 落库 user 消息
→ 取最近 N 轮历史 → registry.get_provider(model_key)
→ provider.generate(messages)（本地走线程池 + 锁）
→ 落库 assistant 消息（含 model_key、status）
→ 更新 conversation.updated_at
→ 返回 {user_message, assistant_message}
```

### 7.3 会话切换模型
只更新 `conversations.model_key`，不改历史消息；新消息使用新模型。

## 9. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 本地模型显存/内存不足 | 加载 OOM、进程退出 | 单模型单例、`torch_dtype=auto`、限制 `max_new_tokens`、加载失败只标记不崩溃 |
| 本地模型加载慢 | 首次请求超时 | 首次调用前先"加载模型"接口预热，前端显示状态 |
| 远端模型不稳定 | 429/超时 | 统一捕获异常转成 502 + 可读文案，前端提示重试 |
| pt 格式兼容问题 | `from_pretrained` 参数不匹配 | 先写 `scripts/local_model_demo.py` 实测跑通，再接入系统 |
| 前后端字段不一致 | 联调返工 | 以 `docs/API设计.md` 为准，后端先出 OpenAPI，前端按 schema 生成 |
| 并发生成导致锁等待 | 多标签页同时发 | 锁 + 明确排队提示，V2 再做队列与流式 |
